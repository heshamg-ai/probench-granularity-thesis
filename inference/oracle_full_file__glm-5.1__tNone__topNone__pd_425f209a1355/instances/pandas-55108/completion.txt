Looking at the `Index.difference` method, I can see that when `_should_compare` returns `False` (meaning the two indexes have non-comparable dtypes, so their intersection is empty), the method currently calls `self.rename(result_name)` and then potentially `result.sort_values()`. The `sort_values()` call on a DatetimeIndex is expensive as it performs a full sort.

For the disjoint case where we know nothing matches, sorting is equivalent to simply checking if the index is already sorted. I can optimize this by checking monotonicity first, which for DatetimeIndex is an O(1) cached property lookup, and only falling back to `sort_values()` if it's not already monotonic.

This preserves exact semantics: if `sort=None` or `sort=True`, the result is sorted (either already sorted via fastpath, or sorted via `sort_values()`). If `sort=False`, no sorting is attempted.
